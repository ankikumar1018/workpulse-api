This file gives AI coding agents the minimum project-specific context needed to be productive in the backend repository.

## Scope

- Applies to: backend repository only
- Root: this folder
- Primary runtime: Python 3.14
- Default Git branch: main

## Architecture Boundaries

- [app/api](app/api): HTTP routes, transport schemas
- [app/application](app/application): orchestration/use-cases
- [app/domain](app/domain): business rules/entities
- [app/infrastructure](app/infrastructure): DB and external adapters
- [app/workers](app/workers): async/background/webhook processing
- [alembic](alembic): DB migration scripts
- [tests](tests): automated tests

Do not place domain logic in api/infrastructure layers.

## Implementation Phases (Execution Order)

Build in this exact order unless explicitly changed by the user.

### Phase 1: Core API and business data

- `organizations`, `projects`, `departments`, `workers`, `work_items`, `templates`, `schedules`, `messages`, `audit_logs`
- Deliver CRUD + validation + tenant scoping + baseline indexes.
- Keep scope lean; avoid introducing advanced framework tables in this phase.

### Phase 2: Authentication and access

- `users`, `auth_identities`, `refresh_sessions`
- JWT access + refresh rotation is the default auth strategy.
- Role starts as a constrained choices field with only `admin` active.

### Phase 3: Scale and advanced capabilities

- Add advanced RBAC, high-volume reliability, compliance, and extensibility tables only when needed.
- Examples: permissions matrices, retry/event ledgers, webhook inbox, retention/privacy workflow tables, custom-field subsystem.

## Canonical Commands

Run from backend root.

- Install deps (dev): `uv sync --group dev`
- Run tests: `uv run pytest`
- Run tests with warnings shown: `uv run pytest -Wd`
- Lint: `uv run ruff check .`
- Format check: `uv run black --check app tests`
- Import order check: `uv run isort --check app tests`
- Type check: `uv run mypy app`
- Start API (dev): `uv run fastapi dev app/main.py --port 8000`
- Apply migrations: `uv run alembic upgrade head`
- Generate migration: `uv run alembic revision --autogenerate -m "Describe change"`

If dependencies change, run `uv lock` and include `uv.lock` in the same commit.

## Database and Containers

- Use `docker compose`, not `docker-compose`.
- Start DB only: `docker compose up -d postgres`
- Compose includes optional pgAdmin service.

## Quality Gates Before Commit

Run all:

1. `uv run ruff check .`
2. `uv run black --check app tests`
3. `uv run isort --check app tests`
4. `uv run mypy app`
5. `uv run pytest`

For non-trivial backend changes, prefer this order:

1. `uv run ruff check .`
2. `uv run mypy app`
3. `uv run pytest -Wd`

## Known Pitfalls (Important)

- Keep Python target settings aligned with 3.14 in tooling config.
- FastAPI test client path currently relies on `httpx2` in dev/test dependencies.
- `python-multipart` must remain compatible with FastAPI standard extras.
- `psycopg[binary]` version must support cp314 wheels.
- Hatch build config is explicit for package discovery (app package); do not remove hatch target sections in [pyproject.toml](pyproject.toml).
- Keep branch naming and pushes on `main`.
- Avoid destructive Git commands (`reset --hard`, force push) unless explicitly requested.
- Do not mix domain rules into [app/api](app/api) or [app/infrastructure](app/infrastructure).

## Database and Migration Safety

- Every schema change must include an Alembic migration.
- Review autogenerated migration scripts before applying.
- Keep migration files focused and reversible when practical.
- If models and migrations disagree, fix both in the same change.
- Keep table design additive across phases; do not introduce phase-3 complexity in phase-1 migrations unless explicitly requested.

## Authentication Strategy

- Default: JWT for API authentication.
- Access tokens should be short-lived; refresh tokens should be rotated and revocable.
- Store refresh token hashes (not raw refresh tokens).
- Social login must be modeled through `auth_identities` (provider mapping), not by changing core business tables.
- Google/OIDC support should be additive and must not break email/password flows.

## Field and Naming Rules

- Prefer explicit state fields (`status`, `delivery_status`, `priority`) over many boolean flags.
- Avoid vague names like `flag`, `enabled`, `processed`.
- Use boolean fields only for true binary facts with clear names (`is_active`, `is_deleted`, `is_verified`).
- Keep enum/choices constraints strict and intention-revealing.
- New schema fields must include a clear business purpose and query path.

## Change Scope Rules

- Prefer minimal diffs and avoid unrelated refactors.
- Preserve existing public API behavior unless a change is explicitly requested.
- Add or update tests for behavior changes in the same PR.

## Documentation Hygiene

- Prefer linking existing docs over duplicating content.
- If behavior changes, update:
  - [README.md](README.md) for setup/workflow changes
  - [pyproject.toml](pyproject.toml) for toolchain changes

## When Unsure

- Follow existing patterns in neighboring modules.
- Make small, test-backed changes.
- Favor incremental PR-safe edits over large rewrites.
