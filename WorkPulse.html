Project Identity & Repository Strategy

This is the architectural baseline for the MVP. The platform is API-first: the backend is the system of record, the admin web app is an API consumer, and future Android/iOS clients can consume the same versioned API.

PROJECT NAME
WorkPulse

Working product name for the workforce communication automation platform.

BACKEND REPOSITORY
workpulse-api

FastAPI backend, domain logic, APIs, scheduling and messaging integrations.

FRONTEND REPOSITORY
workpulse-admin

Next.js + TypeScript administrative web application.

Architect decision: two repositories.

Use workpulse-api and workpulse-admin as separate repositories for the MVP. This gives independent deployment, release cadence, dependency management and ownership while enforcing a clean API boundary. A future mobile application becomes another API consumer instead of requiring a backend redesign.

workpulse-api — Backend Repository

  • app/api/ — REST endpoints, request/response schemas and API dependencies.
  • app/domain/ — entities, value objects and business rules.
  • app/application/ — use cases and application orchestration.
  • app/infrastructure/ — PostgreSQL, Cloud Tasks, WhatsApp and external adapters.
  • app/workers/ — asynchronous task/message execution entry points.
  • tests/ — unit, integration and provider/contract tests.
  • alembic/ — versioned database migrations.
  • Dockerfile and docker-compose.yml — local development environment.

Primary responsibility: all security-sensitive and business-critical behavior, including tenant isolation, authorization, worker/primary-contact selection, work status, template rendering, scheduling, idempotency, delivery tracking and channel integrations.

workpulse-admin — Frontend Repository

  • app/ — Next.js routes/pages.
  • features/ — project, department, worker, work, template and scheduling modules.
  • components/ — reusable UI components.
  • lib/api/ — typed API client and request handling.
  • types/ — API/client types.
  • tests/ — component and end-to-end frontend tests.
  • Dockerfile — containerized development/production runtime.

Primary responsibility: administrator experience, forms, dashboards, navigation, client-side validation and presentation. The frontend must never directly access PostgreSQL or own business-critical scheduling/messaging rules.

Branching & Collaboration

  • main is protected and represents the releasable branch.
  • Use short-lived branches such as feat/project-management, feat/message-scheduling and fix/webhook-idempotency.
  • Every change is merged through pull request review and automated quality checks.
  • Backend and frontend releases are independent; do not force synchronized version numbers.
  • Breaking API changes require an explicit API-versioning decision rather than silently breaking the frontend.
Future-proofing: if Android/iOS is introduced, add a dedicated client repository rather than coupling mobile logic into the web application. If SMS is introduced, add an SMS channel adapter behind the existing messaging abstraction. If two-way communication is introduced, add inbound-message/conversation capabilities to the backend without changing the repository boundary.

5. Scheduling & Reliability Design

✓ DESIGNED

Scheduling must create logical communication jobs; infrastructure executes them. A queued task is never treated as proof that a message was sent.

ConcernDecision
Time windowStart time + end time + interval + timezone.
ExecutionCloud Tasks invokes an authenticated internal job endpoint.
FreshnessProcessor evaluates current work/worker/schedule state at execution time.
RetryTransient errors retry; permanent errors become failed.
Duplicate protectionDatabase-backed logical job/message idempotency.
CancellationInactive/changed schedules invalidate obsolete jobs.
Rate limitsQueue/task configuration plus provider-aware dispatch controls.
TimezoneStore timezone explicitly; persist timestamps in UTC.

14. Architecture Guardrails for the Team

  • API is the product boundary. Web and future mobile clients must consume the same API.
  • Domain is provider-agnostic. No WhatsApp/GCP-specific business rules in the core.
  • Modular monolith first. Extract services only when a real operational boundary appears.
  • Database is the source of truth. Queues/tasks are execution mechanisms, not business state.
  • Every message is traceable. Project → schedule → job → message → provider → delivery.
  • Every retry must be safe. Idempotency is a correctness requirement, not an optimization.
  • Design for change, don't implement speculative features. SMS/mobile/two-way have extension points but remain outside MVP.
  • Docker early, cloud late. Developers use containers from the first implementation; deployment infrastructure comes last.
